# LOCODE 도구 호출 호환성 개선

검증일: 2026-11-02.

## 수정 파일

- `src/locode.js`: 공통 응답 파서, 모드, 검증·실행 루프, 중복 방지, 재개 상태와 UI.
- `test.mjs`: 설명문 JSON 추출의 기존 기대값 수정, 새 LOCODE 테스트 연결.
- `tests/locode.mjs`: 파서·도구·승인·Java 통합 흐름·중단·재개·제한 회귀 테스트.
- `tests/locode.spec.mjs`: 실제 브라우저에서 미리보기·승인·거부·명령·복원 확인.
- `tests/locode-live.mjs`: 선택 실행하는 실제 Ollama 모델 점검(백엔드는 모의).
- `LOCODE_DESIGN.md`, `VALIDATION.md`, 이 문서: 동작과 검증 범위 기록.

## 확인한 원인과 호출 흐름

`locodeSend`는 `ensureModelInfo` 이후 capabilities의 `tools`로 실행 권한을 결정한다.
`locodeTier`의 모델 이름은 추천 등급 표시용이며 쓰기 권한을 부여하지 않는다.
`callModel` → `ollamaFetch` (`src/net.js`) → Rust `ollama_request` → `/api/chat`
응답을 받고, `message.tool_calls` 또는 `message.content`를 처리한다.
일반 CHAT 경로와 공유 전송 계층은 변경하지 않았다.

기존 코드에는 세 가지 문제가 있었다.

1. `salvageToolCalls`가 텍스트 호출을 복구한 뒤 `locodeSend`가 읽기·계획·finish만
   남겨 쓰기와 명령을 버렸다. 유효한 `write_file`도 실제 실행에 도달하지 않았다.
2. 파서가 설명문 중간의 코드 블록과 첫 `{`부터 마지막 `}`까지 추출했다.
   예시나 파일 내용이 실행 후보가 될 수 있었다.
3. Native/JSON 루프가 따로 구현되어 종료 검증, 오류, 반복 감지가 달랐다.
   다음 요청에는 대화만 전달되어 실제 변경·실패·검증 상태가 빠졌다.

현재는 `decodeToolResponse` → `validateLocodeArgs` → `execAction` 순서로 통합한다.
`finish`도 같은 인수 검증을 거친다. JSON/호출 형식 오류는 예시와 함께 최대 두 번
재요청하고, 잘못된 이름·인수는 실행하지 않고 수정 가능한 도구 결과를 돌려준다.
실행 실패·거부·정책 차단·명령 실패는 연속 실패 한도에 반영한다.
형식 복구 실패 시 원문 전체를 대화나 감사 로그에 추가하지 않는다.

## 모드

프로젝트 하단의 도구 호출 메뉴로 선택하며 대화별로 저장한다.

|모드|요청과 처리|
|---|---|
|Native Tool Calling|`tools`를 전송하고 공식 `tool_calls`를 요구한다. 본문 호출만 오면 형식 재요청 후 제한에 따라 중단한다.|
|Structured JSON|`format`에 도구별 필수 인수·자료형을 포함한 JSON Schema를 전송한다. `action`과 인수의 JSON 객체로 작업을 제안하고 동일한 실행 경로로 처리한다.|
|Auto (기본)|Native로 시작하고 명시적 본문 호출도 처리한다. 유효한 본문 호출 응답이 두 번 확인되면 해당 실행에서만 Structured JSON으로 전환한다. 기존 결과와 계획을 보존하고 Native 대화 쌍을 JSON 대화로 변환한다.|

tools capability가 없는 모델은 어떤 메뉴를 선택해도 읽기·검색·계획·finish만
허용한다. Structured JSON 선택은 쓰기 권한 부여가 아니다.
모드 자동 전환에는 모델 이름 정규식을 사용하지 않는다.
웹 검색이 활성화된 도구 지원 모델은 전환 후에도 검색 스키마와 기존 승인을 유지한다.

`format`의 JSON Schema 사용은 [Ollama 공식 문서](https://docs.ollama.com/capabilities/structured-outputs)를 따른다.
스키마 출력도 신뢰하지 않고 실행 직전에 다시 검증한다.

## 허용 형식과 중복 방지

- 공식 `message.tool_calls`: 항상 본문보다 우선한다.
- 본문 전체가 JSON인 `{name, arguments}`, `{action, ...인수}`.
- 기존 별칭 `{tool, args}`, `{function: {name, arguments}}`.
- 응답 전체를 감싼 JSON 코드 펜스 또는 단일 `<tool_call>...</tool_call>`.
- 위 호출들의 전체 JSON 배열. 응답 내 같은 호출은 키 순서·설명 차이와 무관하게 합친다.

설명 앞뒤에 JSON을 삽입하거나 파일 내용의 JSON을 중첩한 응답은 실행하지 않는다.
잘못된 JSON, 알 수 없는 도구, 잘못된 자료형·인수·호출 필드는 거부한다.
임의 자연어의 중괄호를 탐색하지 않으며 여러 태그의 부분 추출도 하지 않는다.
외부 파일 자체를 파서에 넣지 않는다. 모델이 외부 지시를 그대로 호출로 재출력하는
일반적인 프롬프트 인젝션까지 완전히 판별하는 것은 아니다.

같은 실행에서 이미 적용한 변경과 시도한 명령은 결과를 재사용한다. 명령 실패·거부도
동일한 명령을 자동 재실행하지 않는다. 설명(summary/why)은 작업 식별에서 제외한다.
이미 같은 내용인 파일은 미리 읽어 확인한 뒤 다시 쓰지 않는다.

## 승인과 보안

지원 도구: list_dir, read_file, search, propose_plan, write_file, edit_file,
move_path, delete_path, run_command, finish. 텍스트 호출도 기존 도구와 동일하게 처리한다.

파일 변경은 기존 diff·편집 미리보기와 `resolveApproval`을 거친 뒤 기존 Rust
`locode_write_file` / `locode_edit_file` / `locode_move` / `locode_delete`로 전달된다.
미리보기 생략 메뉴에서도 Rust `mutate`의 네이티브 승인은 유지한다.
명령은 기존 정책 확인과 승인 카드 뒤 `locode_run`으로 전달한다.
Rust는 `confirm`과 프로젝트·작업에 바인딩된 일회성 `grant.validate`를 통과해야
실제로 변경하거나 프로세스를 생성한다. 프런트엔드의 승인 boolean으로 대체하지 않는다.

Rust 소스는 이번 수정에서 변경하지 않았다. 프로젝트 외부 접근, 비밀 파일·마스킹,
정션·하드 링크, revision 충돌, 취소, 명령 시간·출력 제한과 복구 정책을 그대로 적용한다.
모델의 완료 선언은 검증 성공의 근거가 아니다. 종료 보고는 실제 commandRuns 상태를
별도로 표시하며 javac도 빌드 검증으로 분류한다.

## 중단과 재개

실제 실행마다 대화 객체에 최대 80개의 `locodeExecution` 메타데이터를 저장한다.
도구 이름·성공 여부·안전한 실패 분류/원인·경로·명령 종료 코드/상태를 기록하고,
실행 원문·파일 내용·명령 인수·모델 응답 원문을 이 메타데이터에 추가하지 않는다.
탐색/계획/파일 변경/검증/보고 상태도 표시한다.

기존 `src/app.js`와 IndexedDB 저장 계층은 대화 객체 전체를 저장하므로 별도 저장
형식 변경 없이 복원한다. 다음 요청의 시스템 문맥에 계획의 완료 단계, 마지막 성공과
실패, 변경 경로, 실제 명령 상태를 전달한다. 오래된 대화에는 이력이 없을 수 있다.
변경 경로에 다시 쓰려면 현재 파일 또는 부모 디렉터리를 재확인해야 한다.
같은 내용은 재작성하지 않으며, 새로운 변경과 명령에는 매번 기존 승인 정책을 적용한다.
과거 명령이나 승인 자체를 복원해서 재실행하지 않는다.

시스템 규칙과 이번 사용자 요청을 유지하고 최근 대화만 전달한다. 요청 예산에는
도구/출력 스키마도 포함한다. 오래된 도구 대화 쌍부터 줄이고도 초과하면 명확하게
중단한다. 기존 3분·24회·누적 32,000 추정 토큰·연속 실패 3회·반복 감지를 유지한다.

## 검증 결과와 범위

|검증|결과|
|---|---|
|`node test.mjs`|통과. 기존 security/transport/research/storage 및 새 LOCODE 회귀 테스트|
|`npm run test:ui`|7개 통과. 새 LOCODE 승인·거부 UI 2개와 기존 CHAT/검색/저장 5개|
|`cargo check --locked`|통과|
|`cargo test --locked`|21개 통과. 제한 환경에서는 DPAPI/폴더 접근 관련 3건이 실패했으나 일반 사용자 환경 재실행은 전부 통과|
|`node tests/locode-live.mjs`|실제 qwen2.5-coder:7b 응답으로 탐색→읽기→계획→쓰기 승인 요청 확인|

`tests/locode.mjs`는 실제 프런트엔드 루프와 승인 함수를 사용하고 Ollama/Rust RPC를
모의한다. 사용자 제공 응답을 그대로 회귀 데이터에 포함한다. Java 생성, 승인, 컴파일·실행
요청, 결과 반영, 보고, 쓰기/명령 거부, 부분 편집, 이동·삭제·검색, Native 우선/중복,
JSON 실패·인수 실패·수정 재시도, 중지·늦은 응답 폐기, 시간·토큰·호출·컨텍스트 제한,
저장 왕복 후 재개와 동일 파일 재작성 방지를 확인했다.
컴파일·실행의 모의 성공은 실제 Java 컴파일 성공이라는 뜻이 아니다.

실모델에서는 첫 두 번 모두 `tool_calls` 없이 본문 JSON을 반환했고 이후 JSON 모드로
전환되었다. `list_dir`, `read_file`, `propose_plan`, `write_file` 순으로 실행 경로에
도달했다. 실모델 테스트도 백엔드/승인 창은 모의이며 최종 변경을 거부하도록 했다.
따라서 실제 파일 적용은 0건이고 실모델의 실제 Java 컴파일/실행 및 실제 Windows
승인 창을 포함한 전체 데스크톱 검증은 미수행이다. 새 통합 테스트의 보안 검증 범위는
RPC 경로/거부 결과 반영이며, 네이티브 승인 바인딩 자체는 Rust 테스트로 확인했다.

실모델 선택과 응답은 비결정적이다. 도구 지원 모델의 모든 작업 성공을 보장하지 않으며
자동 전환은 한 실행에만 적용한다. 중지/거부 후 재개는 새 요청과 새 승인이 필요하다.
